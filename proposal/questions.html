    Management security Q&A worksheet

    50 practical questions for reviewing the Common foundation and three security options. Answers describe the proposed design, not proof that controls are deployed; unresolved choices and budget limitations are stated explicitly.

    Common foundation and account security

    Q01

    What exactly is management approving, and who remains accountable?

    • Approve the Common foundation plus one complete protection option, not three overlapping purchases; all options assume at most 100 administrators and mandatory two-factor authentication. [Proposal: Named owners, segregation of duties and a control register] [Proposal: Budget assumptions]
    • Name owners for cloud administration, application security, incidents and billing, and require someone other than the change author to approve production work. [Proposal: Named owners, segregation of duties and a control register]
    • A RACI responsibility matrix and control register must record the owner, test evidence, accepted exceptions and review dates; AWS operating a service does not transfer these decisions to AWS. [Proposal: Named owners, segregation of duties and a control register] [Proposal: What the team still owns]

    Q02

    Why separate AWS accounts rather than just use different networks?

    • The proposed organization separates management, production, development, security tooling, log archive and backups, with security services delegated to the security-tooling account. [Proposal: One AWS Organization with purpose-built accounts]
    • The purpose is to limit the impact of a production or development compromise and keep audit evidence and recovery copies outside application administrators’ ordinary control. [Strategy: Account security] [Proposal: An immutable, organization-wide audit trail] [Proposal: Backups that an attacker or administrator cannot delete]
    • Management must settle the production-account migration before launch where practical; account separation is an implementation task, not something the organization structure alone completes. [Proposal: One AWS Organization with purpose-built accounts]
    Back to worksheet overview
    Q03

    Do SCPs prevent every administrator from overriding security controls?

    • An SCP sets the maximum permissions available to users and roles in member accounts, including member-account root users; it does not grant access by itself. [AWS SCP limitations]
    • The statement needs limits: SCPs do not protect the management account or restrict service-linked roles, so “no administrator can bypass” is not an organization-wide absolute. [AWS SCP limitations]
    • The proposal uses SCPs to deny disabling security services, creating permanent credentials and making unauthorized network changes, with tightly controlled security-automation exceptions. [Proposal: Service control policies that no administrator can bypass]
    Back to worksheet overview
    Q04

    How do we avoid locking out legitimate operations with an SCP?

    • Deploy the policies in development first, exercise actual deployment and recovery tasks, and follow the proposed week-long test period before production enforcement. [Proposal: Service control policies that no administrator can bypass]
    • Explicitly permit required global services when restricting Regions and document the narrowly scoped pipeline or security-automation roles allowed to perform sensitive actions. [Proposal: Service control policies that no administrator can bypass]
    • Treat policy simulation as supporting evidence, not a substitute for real workflow tests; any policy change must be reviewed and alerted because the allowed exceptions are security-sensitive. [Proposal: Service control policies that no administrator can bypass] [Proposal: Changes only through reviewed code and keyless pipelines]
    Back to worksheet overview
    Q05

    How is the organization management account protected if SCPs do not cover it?

    • Keep application workloads out of it and restrict entry to at most two named administrators using IAM Identity Center with hardware-backed authentication. [Proposal: Management account, root users and break-glass]
    • Protect the root user with two hardware MFA keys stored separately, no access keys, a documented custody process and an alarm for every use. [Proposal: Management account, root users and break-glass]
    • Maintain two controlled emergency identities, alert the security owner whenever either is used, and perform a post-use review rather than treating them as ordinary admin accounts. [Proposal: Management account, root users and break-glass]
    Back to worksheet overview
    Q06

    What do resource control policies add beyond user permissions and SCPs?

    • RCPs limit access to supported resources, complementing policies that govern what our own identities can do; the proposed perimeter covers services such as S3, KMS, Secrets Manager and SQS. [Proposal: Resource control policies]
    • The design denies unapproved outside identities and unencrypted requests where supported, and restricts AWS services acting on resources for another organization. [Proposal: Resource control policies]
    • Inventory external access with IAM Access Analyzer before enforcement and explicitly approve necessary integrations such as vendor log delivery; do not assume every service or resource is covered identically. [Proposal: Resource control policies]

    Q07

    Which insecure defaults are actually removed?

    • Enable all S3 Block Public Access settings, encrypted EBS disks and restrictions on publicly shared machine images and snapshots, enforced through organization policies and account baselines. [Proposal: Secure defaults enforced by declarative policies and account baselines]
    • Require Instance Metadata Service v2 (IMDSv2), restrict allowed machine-image publishers and apply VPC Block Public Access with documented exceptions for required public-entry and NAT subnets. [Proposal: Secure defaults enforced by declarative policies and account baselines]
    • Use mandatory resource tags for ownership, environment and data class, including the tags that trigger backup coverage, and check the resulting resources rather than relying only on the template. [Proposal: Secure defaults enforced by declarative policies and account baselines] [Proposal: Backups that an attacker or administrator cannot delete]

    Q08

    How do named AWS accounts, roles and two-factor sign-in work?

    • Use IAM Identity Center federated to the client identity provider, with Microsoft Entra ID recommended; its own directory is the documented fallback with manual joiner, mover and leaver handling. [Proposal: Named identities through IAM Identity Center with mandatory MFA]
    • Require MFA through the actual identity provider and use FIDO2 security keys or passkeys for the most powerful roles, with SMS and email codes disabled in the proposed policy. [Proposal: Named identities through IAM Identity Center with mandatory MFA]
    • Use Viewer, Operator, Deployer and Auditor permission sets instead of IAM users, with up to eight-hour ordinary console sessions, one-hour administrator sessions, quarterly access review and inactivity controls. [Proposal: Named identities through IAM Identity Center with mandatory MFA]

    Q09

    What is logged, and how long do we retain it?

    • CloudTrail records account activity, AWS Config records settings, and the shared archive receives load-balancer, edge, network, cluster, database and administrator-access logs. [Proposal: An immutable, organization-wide audit trail]
    • The proposed security/audit retention is one year readily available plus six years archived, while operational logs have a shorter 30–90-day window and access logs one year. [Proposal: An immutable, organization-wide audit trail]
    • Classify each stream and approve its retention before locking it; the application must also record who changed a guidance object, because infrastructure logs alone do not explain the business change. [Proposal: An immutable, organization-wide audit trail] [Strategy: Data protection]

    Q10

    Why do we need GuardDuty, Security Hub, Inspector, Config, Access Analyzer and Macie?

    • GuardDuty detects suspicious activity, Inspector finds vulnerable software, AWS Config records and checks resource settings, and Security Hub consolidates security findings and standards results. [Proposal: Managed detection with alert-only routing] [Proposal: An immutable, organization-wide audit trail]
    • IAM Access Analyzer examines external and unused access, while Macie provides the sensitive-data discovery capability assigned to the central security account in the strategy. [Proposal: One AWS Organization with purpose-built accounts] [Strategy: Account security]
    • These tools answer different questions and still require owners to tune findings, choose coverage and fund usage; enabling them is not proof that incidents are handled. [Proposal: Managed detection with alert-only routing] [Proposal: Common cost allowance]

    Q11

    Who receives an attack alert, and what response is promised?

    • P1 pages an on-call phone around the clock, P2 goes to chat and email, and P3 becomes a weekly digest, routed through the proposed Security Hub, EventBridge and SNS process. [Proposal: Managed detection with alert-only routing]
    • The design targets P1 acknowledgement within 15 minutes and containment within one hour; these are operating targets to staff and rehearse, not automatic AWS guarantees. [Proposal: Managed detection with alert-only routing]
    • Every alert needs a runbook and an owner, and the team tests routing monthly using sample findings so that a paid detection service does not become an unread mailbox. [Proposal: Managed detection with alert-only routing]
    Back to worksheet overview
    Q12

    What happens if an attacker deletes the live database or encrypts its data?

    • The proposal combines at least seven days of database point-in-time recovery with daily snapshots retained for 35 days and copies in a separate backup account. [Proposal: Backups that an attacker or administrator cannot delete]
    • Quarterly restore exercises must prove that the copies, permissions and encryption keys work together, recording recovery time and possible data loss for business approval. [Proposal: Backups that an attacker or administrator cannot delete]
    • No fixed recovery-time or recovery-point guarantee is approved by the mere existence of backups; use measured restore results to agree acceptable outage and data-loss limits. [Proposal: Backups that an attacker or administrator cannot delete] [Strategy: Recovery]
    Back to worksheet overview
    Q13

    Can an administrator undo a mistaken immutable-backup setting?

    • AWS Backup Vault Lock compliance mode has a configurable grace period of at least three days during which the lock can be changed or removed. [AWS backup protection]
    • After that period, the lock cannot be changed or deleted while the vault contains recovery points, and protected backups cannot be deleted before their lifecycle completes. [AWS backup protection]
    • Before the grace period ends, validate retention, copy jobs and costs, especially any “Always” retention setting; an incorrect immutable policy can create long-lived obligations. [AWS backup protection]
    Back to worksheet overview
    Q14

    Does keeping the database in one Region settle data residency and privacy?

    • CloudFront serves cached public content worldwide, while Imperva needs explicit contractual commitments about processing and log locations; neither is resolved merely by the database location. [Proposal: Data protection, minimization and what the edge may hold] [Proposal: Protect personal data across both providers]
    • Identify what is public, personal or sensitive in responses and logs, and obtain approval for any cross-border processing or retention exception before launch. [Proposal: What the team still owns and the approval condition] [Proposal: Protect personal data across both providers]

    Administrator access and recovery access

    Q15

    What does Verified Access replace, and what does it not replace?

    • It replaces the proposed everyday Client VPN entry path for private administration with application-specific access: one HTTP endpoint for the admin website and two technical endpoints. [Proposal: Administrator console] [Proposal: Engineering access]
    • Verified Access evaluates trust-provider data against access policies, with application requests denied until an allow policy is defined. [How Verified Access works]
    • It does not replace MFA, AWS permissions, Kubernetes permissions, database credentials or application authorization; those controls remain separate layers. [Proposal: Administrator console] [Proposal: One identity per workload, one login per service]
    Back to worksheet overview
    Q16

    Where exactly is 2FA enforced, and is an identity licence included?

    • Enforce MFA in IAM Identity Center when it holds the users, or through the federated identity provider’s authentication policy; purchasing Verified Access alone does not configure the proposed MFA requirement. [Proposal: Named identities through IAM Identity Center with mandatory MFA] [Proposal: Administrator console]
    • For an IAM Identity Center trust provider, AWS requires an organization instance in the same Region as the Verified Access trust provider, so confirm the existing identity deployment before approval. [AWS identity-provider requirements]
    • The worksheet reserves USD 300 per month for additional identity licences, based on a placeholder of 100 people at USD 3, not a verified Entra ID quote. [Proposal: Common cost allowance]

    Q17

    Does the identity-only design verify that an administrator’s device is safe?

    • Not by itself: the baseline proposal identifies the user and applies access policy, while device posture is a separate trust-provider integration rather than an assumed benefit. [Proposal: Administrator console] [How Verified Access works]
    • AWS device trust can require a supported device provider, agent or browser extension, with platform-specific requirements that need testing on the actual administrator machines. [AWS device trust requirements]
    • If device checks are made mandatory, price the provider and operational work explicitly and test blocked, unmanaged and recovery devices before enforcing the policy. [AWS device trust requirements] [Proposal: Budget assumptions]

    Q18

    Why do we need application login and roles after Verified Access has admitted someone?

    • The admin gateway must verify the signed user-context token, while the application retains its own OpenID Connect login and role-based authorization. [Proposal: Administrator console]
    • Test users from different administrator groups against real actions and object boundaries, including a valid user attempting an unauthorized update. [Proposal: Twelve go-live gates with evidence, not dates] [Strategy: Gate: administrator login]

    Q19

    Are administrator countries and obscure hostnames real security controls?

    • The design applies administrator location restrictions at the identity provider and Verified Access policy, while the separate, low-visibility hostname reduces casual discovery. [Proposal: Administrator console] [Proposal: Location checks without blocking emergency readers]
    • Neither replaces MFA or authorization, and IP-derived location is not reliable evidence of a person’s physical location. [Proposal: Location checks with the real client visible at the edge] [Strategy: Location controls]
    • Use a documented, time-limited exception process for legitimate travel or unexpected routing, without weakening the mandatory identity checks. [Proposal: Administrator console]

    Q20

    Does disabling a user immediately terminate every session?

    • Before approval, test removal from groups, disabled identities, MFA resets and active sessions, and record the maximum observed revocation delay and emergency response procedure. [Strategy: Short sessions] [Proposal: Twelve go-live gates with evidence, not dates]

    Can CloudShell save us if Verified Access or the identity provider fails?

    Option 1: Lean AWS

    Q23

    What is the complete traffic path in the lowest-cost option?

    • Public users reach an internet-facing Application Load Balancer protected by AWS WAF and Shield Standard, then the public gateway and private workloads; there is no full-site edge cache. [Proposal: Public entry] [Proposal: Inside the VPC]
    • Administrators use Verified Access to a separate internal load balancer, while technical administrators use the two restricted endpoints rather than the public application path. [Proposal: Administrator console] [Proposal: Engineering access]
    • This removes an additional public-edge vendor but sends public demand into the Region, so it is acceptable only after the surge and HTTPS fallback tests pass. [Proposal: Best fit and trade-off] [Proposal: Management approval condition]
    Back to worksheet overview
    Q24

    Which attacks will WAF block, and how do we avoid blocking legitimate visitors?

    • The proposed rule set combines managed attack signatures, IP reputation, a positive allow-list of public paths and methods, and different rate limits for reads, writes and assets. [Proposal: Public entry]
    • Tune thresholds for mobile carriers that put many people behind one address, and use the required COUNT observation period before enforcement rather than enabling aggressive blocking untested. [Proposal: Public entry] [Proposal: Twelve go-live gates with evidence, not dates]
    • WAF does not validate whether submitted coordinates are truthful or whether a guidance change is authorized; the application must still enforce those business rules. [Proposal: Location checks without blocking emergency readers] [Proposal: Administrator console]
    Back to worksheet overview
    Q25

    Why not block foreign visitors or put CAPTCHA on every public page?

    • Emergency readers physically inside the service area can appear to have foreign IP addresses through roaming, so the proposal does not country-block public reads. [Proposal: Location checks without blocking emergency readers]
    • Apply stronger scrutiny to suspicious writes and validate coordinates, speed and timestamps in the application, instead of preventing people from obtaining safety information. [Proposal: Location checks without blocking emergency readers]
    • Any browser challenge on reads needs accessibility and emergency-load testing; the existing-edge proposal specifically avoids CAPTCHA on public pages and confines attack-time challenge use to the write path. [Proposal: Public entry] [Proposal: Public entry]
    Back to worksheet overview
    Q26

    What happens if the directly exposed application cannot handle an emergency surge?

    • Shield Standard covers common network/transport attacks, but the proposed drill must test 500,000 simulated public users, a separate population from the maximum 100 administrators. [Proposal: Public entry] [Proposal: Management approval condition]
    • The Lean AWS fallback uses DNS failover to a signed static emergency page, and bare S3 website hosting does not supply HTTPS. [Proposal: Detection, response and the emergency fallback in this package]
    • A minimal CloudFront fallback or another approved HTTPS solution must be tested and costed, so this option’s starting budget is incomplete until that gap is resolved. [Proposal: Detection, response and the emergency fallback in this package] [Proposal: Management approval condition]

    Option 2: AWS edge

    Q27

    How is Option 2 different from simply adding another WAF?

    • CloudFront becomes the public front door and can serve eligible public content from edge locations, while AWS WAF evaluates public requests at that edge. [Proposal: Public entry] [Proposal: Cache public content, never private responses]
    • The load balancer is restricted to CloudFront origin-facing addresses and validates a secret origin header, because an address allow-list alone does not identify our distribution. [Proposal: Public entry]
    • The proposal also keeps an origin WAF layer in BLOCK, while administrator access remains on Verified Access and off the public CloudFront distribution. [Proposal: Public entry] [Proposal: Administrator console]
    Back to worksheet overview
    Q28

    What can be cached, and how do we prevent stale or leaked information?

    • Cache approved public assets, map tiles when adopted, and the signed emergency page; do not cache position writes, administrator responses or personalized/private data. [Proposal: Cache public content, never private responses]
    • Exclude sensitive requests from caching entirely, rather than merely removing identifying fields from the cache key and risking a shared cached response. [Proposal: Cache public content, never private responses]
    • Define the maximum acceptable delay for guidance updates, configure cache rules accordingly, and rehearse invalidation and emergency publishing before launch. [Proposal: Cache public content, never private responses] [Proposal: What the team still owns and the approval condition]
    Back to worksheet overview
    Q29

    Will CloudFront failover keep every application feature working?

    • No: CloudFront origin failover supports GET, HEAD and eligible cached OPTIONS requests, not POST or PUT, so a static fallback preserves reading rather than the write workflow. [CloudFront origin failover]
    • Failover depends on configured errors and timeouts after a primary-origin request fails; it is not a promise of zero interruption or instant switching. [CloudFront origin failover]
    • Test both the readable emergency page and the behavior of unavailable writes, including the message users receive and the process for restoring normal service. [Proposal: Detection, response and the edge-served fallback] [Proposal: Twelve go-live gates with evidence, not dates]
    Back to worksheet overview

    • Validate traffic and feature requirements against the Premium allowances, or obtain a pay-as-you-go estimate if traffic stays low; the separate origin WAF is now priced in the worksheet. [Proposal: Compare total edge cost before buying] [Proposal: Public entry]
    • Monthly request and transfer allowances are not concurrent-user capacity guarantees; the emergency traffic model and drill remain approval requirements. [CloudFront pricing] [Proposal: What the team still owns and the approval condition]

    Q32

    What stops someone bypassing Imperva and attacking the AWS origin directly?

    Q33

    Which layer sees the real visitor IP, and why does it matter?

    Internal protection and safe changes

    Q35

    What stops a compromised public service reaching the admin plane?

    • Keep the EKS API private and separate public and administrator workloads into namespaces with restricted pod settings and default-deny network policies in both directions. [Proposal: Inside the VPC]
    • Allow only the needed gateway and service paths, including exact public HTTP routes, and test the implemented network rules using an unauthorized source workload. [Proposal: Inside the VPC] [Proposal: Twelve go-live gates with evidence, not dates]
    • Namespaces are an organizational boundary, not proof of isolation by themselves; the proposed policy enforcement and least-privilege workload permissions are what must be demonstrated. [Proposal: Inside the VPC] [Proposal: One identity per workload, one login per service]

    Q36

    Why give every workload its own AWS identity?

    • EKS Pod Identity maps each Kubernetes service account to an IAM role limited to its required secret, key and AWS actions, instead of sharing a powerful role across services. [Proposal: One identity per workload, one login per service]
    • A compromised devices service should not obtain the admin backend’s secret or database authority, so permission tests must include attempted access to another workload’s resources. [Proposal: One identity per workload, one login per service] [Proposal: One identity per workload, one login per service]
    • Implement the proposed restrictions on Kubernetes permissions and token mounting without breaking the intended Pod Identity mechanism; validate both the denied access and the application’s required credentials. [Proposal: One identity per workload, one login per service]
    Back to worksheet overview
    Q37

    How do database roles prevent a public endpoint exposing everything?

    • Replace the shared superuser login with separate devices, geometry and admin-backend logins, plus a non-login owner and a migration role used only by the release job. [Proposal: One identity per workload, one login per service]
    • Use per-user secrets, RDS Proxy, forced TLS, connection limits and statement timeouts; separate pools help keep a public flood from consuming administrator capacity. [Proposal: One identity per workload, one login per service] [Proposal: One identity per workload, one login per service]
    • Reserve master access for emergency use and alert on owner/master logins, then prove the public account cannot list or modify data outside its specific rights. [Proposal: One identity per workload, one login per service] [Proposal: Twelve go-live gates with evidence, not dates]

    Q38

    • Certificate management, key policies and service compatibility are implementation work, so managed edge encryption must not be presented as end-to-end encryption already completed. [Proposal: Inside the VPC] [Proposal: What the team still owns]

    Q39

    How are releases controlled without storing permanent AWS access keys?
