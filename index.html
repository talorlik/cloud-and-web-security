    Security strategy for the alerting system website and its AWS account

    The plan to make the national population-guidance system trustworthy during an evacuation: always reachable, giving guidance no one can tamper with, and protecting location and medical data.       01 · Executive summary

      The platform is well designed, but the application is not yet safe to expose

      The AWS platform design is unusually mature for this stage: GitHub OIDC, SHA-pinned actions, signed images, a private EKS cluster, an Imperva edge and an admin plane behind a VPN with MFA. The application inside it is not ready. It has no working authentication or authorization, and its device endpoints are open to the internet. This strategy closes that gap first, then removes the structural risks that sit in the current decisions.

      Ten moves that matter most

      1. Close the public device read surface now, at the platform. Change the public HTTPRoutes and Imperva rules so only exact public paths and methods (position post, geo lookups) pass. This needs no change to app/. See CH-01.
      2. Make admin login and authorization (F5, C21) a hard go-live gate. Use OIDC against the chosen identity provider, with per-authority RBAC, and remove the seed admin/admin account and NoOpPasswordEncoder. See SC-05.
      3. Decide the identity provider (B3a). The recommendation is client Entra ID with phishing-resistant MFA, federated to Client VPN, IAM Identity Center, Argo CD and the console. See B3a.
      4. Strip debug and outdated parts from images. Remove JDWP on 8787, run as non-root, replace openjdk:17.0.1 and turn off Swagger in prd. See CH-06.
      5. Move logs to immutable storage with tiered retention, replacing 30-days-and-delete (D35). Keep security logs at least 1 year, in an Object Lock archive. See CH-03.
      6. Limit how long location data is kept (D34) and drop device emails (C15). Permanent retention of personal location data is the largest legal and breach exposure. See CH-04.
      7. Split prd into its own account, inside AWS Organizations (B25). Add log-archive and security-tooling accounts and SCP guardrails. See CH-02.
      8. Switch WAF to BLOCK and Kyverno to Enforce with evidence, before go-live (9.1.7, 9.1.5). Make Imperva origin mTLS mandatory. See SC-11.
      9. De-privilege the database user (D47). Split owner/migration and runtime roles, and replace ddl-auto: update with versioned migrations. See CH-05.
      10. Commission an independent penetration test (B11) after the Phase 12 fixes and before go-live. Retest, then repeat at least yearly. See B11.

      03 · Framework baseline

      How the four frameworks fit together

      Each framework does a different job. ISO 27001 is the management system that owns risk and evidence. The CIS Controls set the order of work. The CIS Benchmarks define the exact configuration. The Well-Architected Security Pillar provides the AWS-native design patterns. Every strategic control in section 10 maps to all four.

      Management system

      ISO/IEC 27001:2022 (+ Amd 1:2024)

      Clauses 4 to 10 define the ISMS: scope, risk assessment and treatment, a Statement of Applicability, internal audit and management review. Annex A has 93 controls in four themes: organizational (37), people (8), physical (14) and technological (34) (Modulos summary of Annex A). Amendment 1 (2024) adds climate-change considerations to the context clauses (ISO). Physical controls A.7 are mostly inherited from AWS and Imperva, and are covered through supplier evidence.

      Prioritization

      CIS Critical Security Controls v8.1

      18 controls, from asset inventory to penetration testing (CIS). They are grouped into Implementation Groups IG1 to IG3. IG3 is meant for organizations handling sensitive data or critical infrastructure (Cisco CIS v8.1 brief). Target: all IG2 safeguards at go-live, then the IG3 safeguards that apply to this system (application-layer filtering, RBAC, code-level checks, application pen testing) within 12 months.

      Configuration

      CIS Benchmarks

      Current versions: AWS Foundations 7.1.0 (CIS AWS), EKS 2.0.0, which covers Kubernetes 1.34 and 1.35 (CIS June 2026 update), PostgreSQL 17 1.1.0 (CIS PostgreSQL), and NGINX 3.1.0 (CIS NGINX). Add the CIS Ubuntu benchmark (nodes, already L1) and the CIS Docker benchmark (images).

      AWS design

      Well-Architected Security Pillar

      Seven best-practice areas: security foundations, identity and access management, detection, infrastructure protection, data protection, incident response and application security (AWS Well-Architected). Its design principles include a strong identity foundation, traceability, security at all layers and keeping people away from data (Security Pillar). Section 07 is organized by these seven areas.

      Version gaps you need to manage

      Security Hub automates CIS AWS Foundations only up to v5.0.0

      Security Hub CSPM supports CIS AWS Foundations v5.0.0, 3.0.0, 1.4.0 and 1.2.0, and does not cover every requirement automatically (AWS Security Hub documentation). CIS has since published v7.0.0 and v7.1.0 (CIS April 2026 update). Strategy: enable the v5.0.0 standard in Security Hub as the automated baseline. Cover the manual and newer v7.1.0 items with AWS Config custom rules or a quarterly CIS-CAT/Prowler run, and record the results as ISMS evidence.

      EKS 1.36 is newer than the CIS EKS benchmark

      CIS EKS 2.0.0 targets Kubernetes 1.34 and 1.35. Apply it to the 1.36 cluster, record any differences as justified deviations in the Statement of Applicability, and re-baseline when CIS publishes a release that covers 1.36.

      Privacy law is a binding overlay, not optional

      Use the EU GDPR as the global privacy baseline. Most modern privacy laws follow its model. Article 5 requires data minimisation, storage limitation, and integrity and confidentiality of personal data (GDPR Article 5). Under Article 35, a Data Protection Impact Assessment is mandatory for large-scale systematic monitoring, and supervisory authorities list tracking people's location as a trigger (EDPB-published DPIA guidance). Continuous location samples from up to 500,000 devices clearly meet that bar. Run privacy management with ISO/IEC 27701:2025, which is now a stand-alone privacy information management system standard (ISO/IEC 27701:2025). Map the local law of each jurisdiction you operate in onto this baseline, and appoint a DPO.

      04 · Threat model

      Who attacks an emergency system, and when

      The attack that matters most comes during a real event or drill, when the site's value and public attention are at their peak. Plan for availability and integrity attacks on the day, and for quiet data theft in between.

      TA-1 · State-sponsored

      Disruption or disinformation during a real event

      DDoS timed to an alert, tampering with guidance content, a fake guidance site, and pre-positioned access through the supply chain or admin accounts. Targets integrity and availability.

      TA-2 · Hacktivists

      Defacement and volumetric DDoS

      Opportunistic. Uses public findings like Swagger UI, open device endpoints and default credentials. Will publish any data leak.

      TA-3 · Data harvesters

      Bulk extraction of location and contact data

      Enumerates GET /device?all=true and email lookups. Re-identification and resale. Highest legal impact under GDPR-style privacy law.

      TA-4 · Insider or compromised partner

      Misuse of legitimate access

      Wide authority user base (Police, Fire, EMS, local authorities, CPA). Shared or leftover accounts, and social engineering of the NOC to scale capacity down.

      TA-5 · Physical / local

      QR sticker replacement on signs

      A cheap way to send people to a lookalike site. It bypasses every cloud control, so it needs physical and domain-trust countermeasures.

      TA-6 · Abuse of public flows

      Fake check-ins and location floods

      Bots post fake arrivals or medical flags to distort occupancy, which misleads first responders. There is no rate limiting today (C14).

      06 · Strategic principles

      Seven rules that decide trade-offs

      When two good controls conflict, such as caching against freshness, or strict blocking against reachability during a surge, apply these principles in order.

      1. Life-safety first: integrity, then availability, then confidentiality. Guidance must be correct before it is fast, and fast before it is private. A cached, signed emergency page is better than a live page that may have been tampered with.
      2. Fail to a known-good degraded mode, never to open. If the cluster is down or overloaded, the edge serves the static emergency page. If authentication fails, admin writes are denied.
      3. Public plane is read-mostly and explicitly allow-listed. Only named paths and methods are routed. Everything else returns 404 at the edge.
      4. Every human is named, federated and phishing-resistant. No shared accounts, no local passwords in the app, and MFA everywhere a person authenticates.
      5. Collect less, keep less. Store the minimum needed for the evacuation purpose, for a set time, then aggregate or delete. Retention is set per data class, not as one rule for everything.
      6. Platform compensates, app remediates. The platform team contains application weaknesses with routing, WAF, policy and network controls, but never treats that as permanent. Each compensating control has an expiry tied to a Phase 12 task.
      7. Everything as code, everything evidenced. Controls live in Terraform, Argo CD and Kyverno. Their state is measured continuously in Security Hub and Config, and the results feed the ISO 27001 evidence pack.

      8.1 WAF rules for common attacks and location enforcement

      CIS 13.10A.8.20, A.8.23WA SEC05ASVS V4

      Short answer: some protection is on by default, but most of what this system needs is manual

      Imperva applies its default account WAF Rules policy to every new site automatically. In that policy, SQL injection, cross-site scripting, illegal resource access and remote file inclusion are all set to Block Request (Imperva policies). Backdoor protection defaults to Auto-Quarantine (Imperva WAF settings). Bad bots are denied and good bots allowed by default (Imperva security settings).

      AWS WAF has no protection until you add rules. A web ACL with no matching rule just applies its default action, normally Allow (AWS WAF default action). Every managed rule group has to be added and tuned.

      Manual in both layers: the public path allow-list, rate limits, country rules, and anything specific to this API.

      How the two layers share the work

      • Imperva (edge, primary): sees the real client IP, absorbs DDoS, filters bots and reputation, and applies the OWASP rules. It is the only layer that can do IP reputation and anonymizer filtering correctly for the public plane.
      • AWS WAF on the origin ALB (second layer): applies AWS managed rules for Java and PostgreSQL attacks, enforces the exact public route allow-list, and adds per-client rate limits. It also guards against anything that slips past Imperva.
      • AWS WAF on the admin ALB: applies managed rules plus a short allow-list of admin routes. It reaches only VPN users, so it doesn't need bot or geo rules.

      Location enforcement

      Location means three different things here, and each needs a different control.

      • Admins: enforce it at the identity provider, not the WAF. Admin traffic arrives over the VPN, so the WAF never sees the admin's real location. If the IdP is Entra ID (B3a), use a Conditional Access location policy to block sign-in from outside the service country (Microsoft Entra). Alert on any VPN connection from an unexpected country (AL-17).
      • Public reading: don't geo-block. With home-routed roaming, the most common setup, a visitor's traffic leaves the internet through their home operator. A tourist in the service area therefore shows up with a foreign IP (ipregistry). A country block would turn away exactly the visitors who most need guidance. Label requests by country instead (rule action Count), and apply stricter rate limits to traffic from outside the service country.
      • Public writes (position samples): enforce it in the application, with WAF help. An IP address can't tell you where a device is. The real control is server-side: reject any coordinate outside the service-area polygon (PostGIS ST_Within), any implausible speed between samples, and any timestamp out of range (R07). At the edge, block anonymizers and hosting providers on this path, and apply the tightest rate limit.
      • Make AWS WAF see the real client. Geo match and rate-based rules can read the client address from a forwarded IP header instead of the request origin (AWS forwarded IP). Configure them to read Imperva's client IP header (B22). That header can only be trusted because the origin accepts nothing but Imperva (WAF-13).
      • Hard country blocking, if the client wants it anyway: apply it only to the write path, with Imperva's ACL Block Countries (Imperva policies), and record the accepted impact on roaming visitors.

      8.7 Admin access without Client VPN: three lower-cost options

      CIS 6.3, 6.4, 6.5, 12.7A.5.15, A.8.5, A.8.20WA SEC02, SEC05

      Short answer: yes, there are cheaper paths, and every one keeps 2FA mandatory

      Client VPN charges per subnet association per hour, plus per connected admin per hour. In the AWS example, one association is $0.10 an hour, and 10 connections for an hour cost $0.50, which is $0.05 each (AWS VPN pricing). Each connection also pays the standard public IPv4 charge. The bill therefore grows with every admin and every hour they stay connected, and it peaks during a real event, when admins stay on for long shifts.

      The three options below replace the VPN with identity-based access. Their costs are flat, or free up to a user count.

      2FA is not optional in any of them. It is enforced at the identity provider (Entra ID Conditional Access, or IAM Identity Center MFA). Super admins need phishing-resistant MFA (FIDO2 or passkeys), and the application's own login sits behind the access layer, not instead of it.

      What has to be covered

      • Browser access for all three admin groups (location, governing organization, super admins) to the Angular console and the admin gateway, which today sit behind the internal admin ALB.
      • Engineering access for super admins only: the private EKS API endpoint, Argo CD, and the DBA path to RDS Proxy. A private EKS endpoint can only be reached from inside the VPC or a connected network (Amazon EKS), so each option needs a path into the VPC for these.

      Shared building block: Session Manager for engineering access

      Options A and C use it, and B can use it too. Run one small EC2 instance in a private subnet as a jump node: no inbound rules, no SSH, SSM Agent only, IMDSv2, rebuilt monthly like the nodes. Super admins sign in through IAM Identity Center with MFA, and open a Session Manager port-forwarding session to the EKS API, Argo CD or RDS Proxy. The remote host doesn't have to be managed by Systems Manager (Session Manager port forwarding).

      • Access is controlled by IAM policy on the session document and the target. Session logs go to CloudWatch and S3.
      • There is no extra Systems Manager charge for this use on EC2. The cost is the small instance itself.
      • This replaces the VPN for the engineering path, and it holds up even if the browser path fails.

      A · Verified Access: pros and cons

      • Stays inside AWS, with no new vendor. Logs go to the log archive like everything else, and residency stays the same (B6).
      • Every request is checked, not just the connection. It can add device posture through a device trust provider.
      • Keeps the internal admin ALB, which Verified Access requires for load balancer endpoints.
      • Cost is flat per application, not per admin. It beats the VPN once about six or more admins are connected full-time.
      • Con: the console needs a public domain name and a public certificate (Verified Access endpoints). The admin name therefore shows up in Certificate Transparency logs (see 8.5). Use a name that doesn't advertise what it is.
      • Con: AWS can't test every OIDC provider, so validate Entra ID in dev first (Verified Access trust providers).

      B · Cloudflare Zero Trust: pros and cons

      • Free while the admin team stays at 50 people or fewer, which is the cheapest secure option at that size.
      • The origin has no inbound path at all. Admin traffic leaves the VPC only as an outbound tunnel.
      • Covers both browser and engineering access with one policy model, and can enforce its own security-key MFA on top of the IdP.
      • Con: adds a second edge vendor alongside Imperva. Admin traffic, identity data and access logs pass through Cloudflare, which needs a residency decision (B6) and a DPA.
      • Con: published hostnames need a zone on Cloudflare (Cloudflare routing). Use a separate admin domain, so the public domain stays on Imperva.
      • Con: engineering access needs the Cloudflare One client on super admin devices, which is lighter than a VPN but still a client.

      C · ALB sign-in with MFA: pros and cons

      • Lowest cost. It reuses the admin ALB, its web ACL and the Session Manager node. Cognito, IAM Identity Center and Session Manager add no licence or per-user charge at 100 admins.
      • No client software for admins. Nothing reaches the console until sign-in and MFA succeed at the ALB.
      • Without Imperva in front, AWS WAF sees the real client IP. The country rule, the anonymous IP list and the IP reputation list all work on the admin plane (compare WAF-12).
      • Con: the admin entry point is internet-reachable, which is the exposure 8.5 advises against. The mandatory controls below exist to offset that.
      • Con: no device posture check unless Entra Conditional Access, with P1, requires compliant devices.
      • Con: with a Cognito user pool, admin accounts live outside the client's directory. Joiners, movers and leavers need a written process and a quarterly review.

      Applies to all three options

      • Remove the Client VPN endpoint only after the new path has run in dev and stg for two weeks, with a written rollback.
      • Keep the break-glass path independent of the IdP (7.2).
      • Point AL-17 at the new access logs (Verified Access, Cloudflare Access or ALB) and at Session Manager session logs.
      • Keep the three admin groups as IdP groups, and map them to access policies: location and governing-organization admins get the console only, super admins get the console plus engineering access.
      • The application's own authentication and RBAC (R01) are still required. The access layer is an outer gate, not a substitute.

      Recommended for this programme: hardened Option C

      There will be at most 100 admins, and budget is the deciding factor. On that basis, the recommendation is Option C with every control in the table below. Option C costs roughly nothing extra per month, against about $1,030 for Client VPN.

      Its weak point, an internet-reachable sign-in page, is offset by four layers before anything reaches the console: mandatory MFA (security keys or passkeys for super admins and governing-organization admins), a country allow-list, a short session, and the application's own RBAC.

      Option A stays the step-up path if the penetration test (B11) or the client's risk owner rejects an internet-reachable admin entry point. It costs about $197 a month more.

      13 · Decisions

      Open decisions, with a recommendation for each

      These come from the brief's list of decisions the strategy needs. Each has a recommended option, so the Steering Committee can approve or reject rather than start from scratch.

      B3a · Identity provider

      Recommend: client Entra ID

      Federated to Client VPN (SAML), IAM Identity Center and the app (OIDC). Use Conditional Access and FIDO2 for super admins. Partner organizations join through B2B guests or their own federation. If the client cannot provide Entra, use IAM Identity Center as the IdP, but plan a manual joiner-mover-leaver process.

      B3c · Admin access path

      Recommend: hardened ALB sign-in with mandatory MFA

      At up to 100 admins with budget as the deciding factor, replace Client VPN with an internet-facing admin ALB. It signs users in through Cognito (or Entra, if P1 is already licensed) with required MFA, uses AWS WAF with a country allow-list, and leaves engineering access to Session Manager. That saves about $1,000 a month against Client VPN. All twelve controls HC-01 to HC-12 are mandatory. Step up to Verified Access (about $197 a month) if the pen test or the risk owner rejects an internet-reachable admin entry point. See 8.7.

      B3b · Admin inventory

      Recommend: named inventory per authority

      Each authority names a sponsor who approves its users. There are three VPN groups mapped to app roles. Quarterly recertification. No shared accounts.

      B6 · Residency

      Recommend: single-Region residency, enforced by SCP

      Deny Regions other than us-east-1. Imperva logs and IdP data stay in the same jurisdiction, or move only with explicit approval. Without a second Region there is no cross-Region DR, so record that as an accepted risk, mitigated by Multi-AZ, a cross-account backup and edge failover.

      B11 · Penetration test

      Recommend: independent firm in Phase 9

      Scope: public site, admin console through the VPN, AWS configuration and the Kubernetes cluster. Schedule it after the Phase 12 fixes, then retest. Repeat yearly, and after major changes, as the DPIA's risk treatment plan requires.

      B12 · NOC caller verification

      Recommend: ticket plus callback plus two-person rule

      Scale-up can be done by one verified caller. Scale-down needs a second approver from a different organization. All requests are logged.

      B22 · Imperva

      Recommend: tier with bot management and a DDoS SLA

      Mandatory origin mTLS. Use only the Imperva client-IP header. Push logs to S3 in us-east-1, and confirm the push before go-live.

      B25 · Prd account

      Recommend: yes, as part of an Organization

      Create it before go-live if the timeline allows, because migrating prd later is harder. Also needed for cost-allocation tags (payer account).

      C21 · App login timeline

      Recommend: hard go-live gate

      The platform can contain the devices endpoints (CH-01) but cannot make up for having no admin login. G1 and G2 are not negotiable.

      C17 · Photo path

      Recommend: presigned upload through the admin plane

      Upload to S3 with a presigned PUT URL. Scan with GuardDuty Malware Protection for S3. Serve through the edge. The bucket is never public.

      9.1.7 · 9.1.5

      Recommend: both before go-live

      WAF BLOCK and Kyverno Enforce, each after a 7-day clean observation window, with the reports kept as evidence.
